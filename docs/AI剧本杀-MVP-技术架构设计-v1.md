# AI 剧本杀 MVP 技术架构设计 v1

## 1. 文档目标

本文档用于定义 AI 剧本杀 MVP 的后端技术架构，作为开发落地依据。  
当前版本约束如下：

- JDK 17
- Spring Boot
- Spring AI
- 单体应用
- 暂不使用数据库
- 前端先采用聊天界面
- 核心目标是验证多角色 AI 剧本杀的互动闭环

---

## 2. 架构目标

MVP 阶段的技术架构要优先满足以下目标：

1. 支撑 1 个剧本内的多角色 AI 对话与剧情推进
2. 支撑玩家自由输入并影响剧情
3. 保证角色人设、知识边界和剧情阶段基本稳定
4. 在不接数据库的前提下完成单局会话管理
5. 为后续引入数据库、RAG、向量检索预留扩展位

---

## 3. 总体架构概览

当前推荐采用单体分层架构：

1. 表现层  
   提供 HTTP / SSE 接口，承接前端聊天页面请求

2. 应用编排层  
   负责游戏流程编排、玩家输入处理、角色调度、剧情推进

3. 领域层  
   定义剧本、角色、会话、状态、事件、线索等核心模型

4. AI 集成层  
   负责 Prompt 拼装、Spring AI 调用、响应解析、摘要与记忆压缩

5. 基础设施层  
   提供内存会话存储、配置加载、本地剧本资源读取、日志与监控

---

## 4. 核心架构思想

本项目不建议把所有逻辑直接丢给大模型，而是采用：

**规则驱动的剧情骨架 + 多角色 Agent 式响应 + 会话状态管理**

其中：

1. 大模型负责语言理解、对话生成、角色表达
2. 业务层负责剧情约束、状态推进、事件判定
3. 会话状态负责保证角色不穿帮、剧情不失控

也就是说，模型负责“演”，系统负责“控”。

---

## 5. 逻辑角色分工

系统内部建议拆成三类核心智能单元。

### 5.1 玩家输入处理器

职责：

1. 接收玩家输入
2. 识别输入意图
3. 判断发言对象
4. 提取关键动作或剧情触发信号
5. 输出标准化的玩家动作对象

### 5.2 剧情调度器

职责：

1. 判断当前剧情阶段
2. 决定哪些角色应当回应
3. 决定是否触发事件
4. 决定是否推进阶段
5. 在剧情偏离时执行拉回策略

### 5.3 角色 Agent

职责：

1. 基于人设、记忆、目标理解当前局势
2. 根据知识边界生成回应
3. 维护个体立场、情绪和秘密
4. 根据局势选择坦白、回避、误导、攻击、沉默等表达方式

## 7. 典型调用链路

### 7.1 开始新游戏

流程：

1. 前端请求创建会话
2. 系统加载预设剧本配置
3. 初始化 GameSession
4. 初始化所有角色初始状态
5. 初始化剧情阶段和事件表
6. 输出开场系统消息

### 7.2 玩家发言后的主链路

流程：

1. 前端发送玩家输入
2. InputProcessingService 分析意图
3. SessionStateService 更新会话上下文
4. StoryDirector 判断是否触发事件或阶段变化
5. ResponseOrchestrator 决定哪些角色回复
6. 针对每个角色拼装专属 Prompt
7. 调用 Spring AI 生成角色回复
8. ResponsePostProcessor 过滤不合规输出
9. 更新角色状态、事件日志、记忆摘要
10. 返回多条角色消息给前端

### 7.3 进入结局

流程：

1. StoryDirector 判断结局条件是否满足
2. EndgameService 生成结局结果
3. 系统输出结局说明
4. 会话状态标记为 FINISHED

---

## 8. 会话与状态管理设计

由于当前版本不使用数据库，会话状态全部以内存方式管理。

### 8.1 会话存储策略

推荐采用：

- ConcurrentHashMap<String, GameSession>

Key 为 sessionId，Value 为完整会话对象。

### 8.2 会话内容

每个 GameSession 至少包含：

1. 会话基础信息
2. 当前剧本定义
3. 当前剧情阶段
4. 角色状态映射
5. 消息历史
6. 已触发事件集合
7. 已公开线索集合
8. 结局状态
9. 最近若干轮摘要

### 8.3 状态管理原则

1. 静态设定与动态状态分离
2. 对话历史不等于记忆摘要
3. 关键剧情状态必须结构化保存
4. 长对话场景下要定期压缩上下文

---

## 9. 无数据库前提下的数据来源

当前版本的数据来源建议全部文件化。

### 9.1 剧本配置

可使用：

- `resources/scripts/*.json`
- `resources/scripts/*.yaml`

内容包含：

1. 剧本元信息
2. 开场设定
3. 角色定义
4. 阶段定义
5. 事件定义
6. 线索定义
7. 结局条件

### 9.2 Prompt 模板

建议使用：

- `resources/prompts/system/`
- `resources/prompts/character/`
- `resources/prompts/story/`

### 9.3 会话存档

MVP 首版可以不做持久化存档。  
如需临时调试，可选做本地 JSON 导出，但不作为正式能力。

## 10. Spring AI 使用建议

### 10.1 建议接入位置

Spring AI 主要用于以下场景：

1. 玩家输入意图分析
2. 角色回复生成
3. 长对话摘要压缩
4. 可选的系统提示补全

### 10.2 当前不建议依赖的能力

由于当前没有数据库与知识库体系，以下能力暂不作为 MVP 重点：

1. 向量数据库
2. RAG 检索链路
3. 多模型路由
4. 复杂工具调用

### 10.3 推荐调用模式

建议封装统一的 `ModelGateway`，避免业务代码直接散落调用 Spring AI。

统一封装以下能力：

1. 模型名与参数配置
2. 系统 Prompt 与用户 Prompt 组装
3. 超时与重试策略
4. 输出格式规范
5. 调用日志

---

## 11. Prompt 架构设计

### 11.1 Prompt 分层

建议至少分四层：

1. 系统级规则 Prompt  
   定义全局输出约束、语言风格、禁止事项

2. 剧本级 Prompt  
   定义世界观、故事背景、真相骨架

3. 角色级 Prompt  
   定义角色身份、秘密、目标、说话方式、知识边界

4. 回合级 Prompt  
   注入当前会话上下文、玩家输入、事件、情绪、摘要

### 11.2 角色 Prompt 内容建议

至少包含：

1. 你是谁
2. 你现在知道什么
3. 你不能知道什么
4. 你此刻的目标是什么
5. 你对玩家的态度
6. 你对其他角色的怀疑或信任
7. 你本轮应该如何表达
8. 你不能说出系统设定

### 11.3 输出约束

建议限制每轮角色输出：

1. 长度适中
2. 不重复别人已说内容
3. 不直接泄露完整真相
4. 不以旁白形式脱离角色
5. 尽量保留人物风格

---

## 12. 剧情控制机制

MVP 必须有明确的剧情控制层，否则纯对话很容易失控。

### 12.1 推荐控制方式

采用“阶段 + 条件事件 + 收束结局”的结构。

#### 阶段

例如：

1. 开场认识
2. 初步试探
3. 线索曝光
4. 冲突升级
5. 真相逼近
6. 结局裁定

#### 条件事件

例如：

1. 玩家连续追问某角色
2. 某条线索被提及三次
3. 角色信任值降到阈值
4. 某秘密达到可揭露条件

#### 收束机制

例如：

1. 达成真相确认
2. 达成错误指控
3. 达成关系崩坏失败结局

### 12.2 拉回策略

当玩家输入过于偏离主线时，系统可通过以下方式拉回：

1. 系统提示当前调查重点
2. 某角色主动抛出关键线索
3. 剧情事件打断闲聊
4. 限制角色在无关话题上的延展

---

## 13. 内存与上下文压缩策略

长对话会导致上下文膨胀，因此需要分层管理。

### 13.1 上下文组成

每轮传给模型的上下文建议由以下部分组成：

1. 角色静态设定
2. 当前剧情阶段
3. 本角色动态状态
4. 关键事件摘要
5. 最近若干轮相关消息
6. 当前玩家输入

### 13.2 压缩策略

建议采用：

1. 最近 6 到 10 轮消息保留全文
2. 更早消息由 SummaryGenerator 压缩为摘要
3. 关键事实单独结构化存储，不依赖摘要恢复

---

## 14. 并发与性能设计

### 14.1 并发原则

MVP 阶段不追求高并发，优先保证正确性。

建议：

1. 单个会话内按回合同步处理
2. 不允许同一会话同时执行两次玩家输入
3. 不同会话之间可并发

### 14.2 角色回复生成策略

推荐：

1. 先串行实现，保证行为稳定
2. 后续如性能不足，再对独立角色回复做有限并行

### 14.3 超时控制

每次模型调用建议配置：

1. 单次超时
2. 重试上限
3. 失败兜底回复

---

## 15. 接口设计建议

### 15.1 创建会话

`POST /api/game-sessions`

返回：

1. sessionId
2. 剧本信息
3. 开场消息
4. 初始角色列表

### 15.2 发送消息

`POST /api/game-sessions/{sessionId}/messages`

请求内容：

1. 玩家输入文本
2. 可选的目标角色

返回：

1. 玩家消息回显
2. 系统事件消息
3. 角色回复列表
4. 当前阶段
5. 可公开线索更新

### 15.3 查询状态

`GET /api/game-sessions/{sessionId}`

返回：

1. 当前阶段
2. 会话状态
3. 角色摘要状态
4. 已公开线索

### 15.4 获取消息流

`GET /api/game-sessions/{sessionId}/messages`

### 15.5 结束会话

`POST /api/game-sessions/{sessionId}/finish`

## 16. 观测与日志

虽然是 MVP，仍建议保留最基本的可观测性。

### 16.1 业务日志

记录：

1. 会话创建
2. 玩家输入
3. 事件触发
4. 阶段切换
5. 角色回复生成
6. 结局达成

### 16.2 AI 调用日志

建议记录：

1. 调用角色
2. 模型名称
3. 调用耗时
4. token 统计
5. 调用是否成功

注意不要直接在生产日志中暴露完整敏感 Prompt。

---

## 17. 错误处理与降级策略

### 17.1 常见异常

1. 会话不存在
2. 会话已结束
3. 模型调用失败
4. 剧本配置加载失败
5. 输出解析失败

### 17.2 降级策略

1. 模型调用失败时返回系统提示并允许重试
2. 单角色生成失败时不阻塞整轮，可由系统旁白兜底
3. 输出异常时进行截断或使用安全默认回复

---

## 18. 后续扩展预留

当前架构需要为以下能力预留扩展位：

1. 数据库持久化
2. 向量检索与长期记忆
3. 多剧本管理
4. 存档与读档
5. 后台配置系统
6. 多玩家模式

建议在接口和领域模型上保持以下分离：

1. Repository 接口先定义，当前用内存实现
2. 剧本加载先走 Loader 抽象
3. 模型调用统一走 Gateway
4. 状态更新集中在领域服务或应用服务中

---

## 19. 当前阶段架构结论

AI 剧本杀 MVP v1 的最佳落地方式，不是复杂化技术栈，而是用一套轻量但边界清晰的 Java 单体架构，把以下三件事先做稳：

1. 多角色的稳定表达
2. 剧情的受控推进
3. 会话状态的持续一致

因此当前推荐架构为：

**Java 17 + Spring Boot + Spring AI + 本地配置化剧本 + 内存会话存储 + 聊天式前端交互**

这套方案足够支撑 MVP 验证，也方便后续自然演进到数据库、RAG 和更复杂的 Agent 协同系统。
