# AI剧本杀-未来扩展规划-v1

## 1. 规划目标

未来的目标不是简单“继续加剧本”，而是把当前 MVP 演进成一个真正可扩展、可运营、可持续生产内容的 AI 剧本杀平台。

扩展方向可以概括为五层：

- 内容层扩展
- 交互层扩展
- 智能体层扩展
- 数据层扩展
- 平台层扩展

---

## 2. 第一阶段扩展：把当前 MVP 做厚

这一阶段的目标，是把现在能玩的原型升级成“更像产品”的版本。

### 2.1 副本体验增强

建议优先补充：

- 更丰富的开场引导
- 更明确的玩家任务说明
- 更自然的环境变化
- 分轮推进机制
- 更有戏剧感的剧情转场
- 线索投放节奏优化
- 指认失败 / 成功后的差异化反馈

### 2.2 角色体验增强

建议补充：

- 更完整的角色卡
- 角色关系图
- 秘密目标
- 支线任务
- 可疑度 / 压力值等状态
- 角色专属可触发事件

### 2.3 前端产品体验增强

建议补充：

- 更成熟的角色气泡视觉系统
- 头像体系
- 剧本信息卡片
- 时间线面板
- 线索卡片详情页
- 角色关系面板
- 音效 / 环境氛围

---

## 3. 第二阶段扩展：从“会话式 AI”走向“Agent 式 AI”

这是未来最关键的一步。

## 3.1 为什么要引入 Agent 思想

当前版本虽然已经有多角色体验，但本质上还是“后端控场 + 模型生成”的统一编排。

如果未来要让角色更鲜活、更稳定、更像真人，就需要引入更明确的 Agent 思想。

Agent 化后，每个角色不再只是一次生成结果，而是具备：

- 自己的身份
- 自己的记忆
- 自己的秘密
- 自己的目标
- 自己的行动边界
- 自己的说话风格

## 3.2 未来的 Agent 设计方向

未来可以把角色拆成以下能力：

- `Role Persona Agent`：负责人格与语气
- `Knowledge Agent`：负责该角色知道什么、不知道什么
- `Intent Agent`：负责角色当前目标与应对策略
- `Safety / Guard Agent`：防止角色越界泄密
- `Director Agent`：负责全局节奏、场景推进、冲突调度

这时系统就不是“一个 AI 扮演很多人”，而更像“多个角色智能体共同构成一场局”。

---

## 4. 第三阶段扩展：数据持久化与知识能力

当前版本不使用数据库是合理的，但后续正式扩展必须进入持久化阶段。

## 4.1 关系型数据库

建议未来接入关系型数据库，例如：

- MySQL
- PostgreSQL

适合存储：

- 副本定义
- 角色定义
- 线索定义
- 剧情阶段
- 会话记录
- 玩家行为记录
- 结案结果

## 4.2 Redis

建议未来接入 Redis，用于：

- 会话缓存
- SSE 状态管理
- 短时上下文缓存
- 高频查询加速

## 4.3 向量数据库

当前版本暂时不必接，但未来很可能需要。

适合接入场景：

- 长剧本内容检索
- 大量线索和人物设定召回
- 记忆片段检索
- 多副本知识库统一召回
- 玩家历史游玩轨迹分析

未来候选：

- Milvus
- pgvector
- Elasticsearch + 向量检索

## 4.4 是否一定需要向量数据库

结论是：

- 当前 MVP 不一定需要
- 当副本数量、文本体量、角色记忆复杂度提升后，大概率需要

也就是说，向量数据库更像“第二阶段以后”的基础设施，而不是第一天就必须接的组件。

## 5. 第四阶段扩展：副本生产系统

如果未来要做成真正的平台，不能只靠手写 Java 里的内存对象定义副本。

必须做内容生产体系。

### 5.1 副本配置化

未来建议把副本改造成配置化结构，例如：

- JSON / YAML 配置
- 数据库编辑
- 副本编辑后台

配置内容包括：

- 副本元信息
- 角色信息
- 阶段设计
- 线索池
- 触发条件
- 结局条件
- 隐藏规则

### 5.2 副本编辑台

未来可以做一个后台：

- 创建副本
- 创建角色
- 编排阶段
- 配置线索
- 配置触发规则
- 调试对话
- 预演结案

这会让内容生产能力从“开发者写代码”升级成“内容策划可参与”。

---

## 6. 第五阶段扩展：多人模式与平台化

这是产品化的高阶目标。

### 6.1 多人联机

未来可以支持：

- 多玩家进入同一局
- 每个玩家抽取不同角色
- AI 角色 + 真人角色混合
- 旁观者模式
- 房主控场模式

### 6.2 观战与复盘

未来可以支持：

- 整局回放
- 关键对话回放
- 线索流转回放
- 推理链路回放

### 6.3 运营能力

未来平台化后可以补：

- 用户系统
- 剧本收藏
- 游玩记录
- 排行 / 成就
- 剧本评分
- 剧本推荐

---

## 7. 技术架构未来演进建议

## 7.1 后端架构

当前适合单体架构，未来可以逐步演进：

### 当前阶段

- Spring Boot 单体应用
- 内存会话 + 简单编排

### 下一阶段

- 单体 + MySQL + Redis
- 副本配置化
- 会话持久化

### 再下一阶段

- Agent 编排层
- 检索层
- 内容平台层
- 运营后台层

## 7.2 前端架构

未来前端可以考虑继续扩展成：

- 官网 / 宣传页
- 玩家游戏端
- 剧本编辑后台
- 运营管理后台

---

## 8. 风险与提醒

未来扩展时要重点注意几个问题：

### 8.1 不要过早做过重架构

例如：

- 一开始就强行上微服务
- 一开始就接复杂 Agent 平台
- 一开始就做重数据库建模

这些都会拖慢核心玩法验证。

### 8.2 Agent 化要服务于体验，不是为了概念

不是“每个角色都叫 Agent”就更高级。

真正有价值的是：

- 角色更稳定
- 角色更像真人
- 角色知道自己该说什么不该说什么
- 剧情推进更自然

### 8.3 内容生产能力迟早是瓶颈

如果未来只靠工程师写死副本，副本数量和维护成本都会成为瓶颈。

所以中期一定要把副本改成配置化或平台化生产。

---

## 9. 推荐扩展优先级

如果按最现实的顺序推进，我建议：

### 优先级 A：先把当前版本做厚

- 优化剧情推进
- 丰富角色卡
- 做更多线索与阶段设计
- 强化前端体验

### 优先级 B：再做持久化

- MySQL
- Redis
- 会话落库

### 优先级 C：再做 Agent 化

- 角色记忆
- 角色目标
- 导演控场

### 优先级 D：再做内容平台

- 副本配置化
- 剧本编辑后台

### 优先级 E：最后做平台化

- 多人联机
- 用户系统
- 运营体系

---

## 10. 总结

一句话总结：

> 当前项目最好的扩展路径，不是立刻追求“大而全”，而是沿着“玩法先成立 -> 数据再落地 -> Agent 再增强 -> 内容平台化 -> 最终平台化”这条路线逐步推进。

这条路线既稳，也最适合把现在已经搭起来的 MVP 真正推成一个有生命力的产品。
