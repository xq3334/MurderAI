# AI剧本杀-多副本角色卡方案-v1

## 1. 当前方向结论

本项目后续采用：

- 多副本选择
- 模式 A：沉浸式扮演
- 用户进入副本后抽取或选择角色卡
- 用户只获取该角色视角下可知的信息
- 其他角色由 AI 扮演
- 系统保留总控层，避免剧情失控

这意味着项目目标已经从“AI 管家陪聊式问答”升级为“带身份约束的 AI 剧本杀平台”。

## 2. 为什么这个方案可行

剧本杀天然适合被拆成结构化系统：

- 公共事实
- 私密设定
- 隐藏动机
- 阶段推进
- 线索投放
- 指控与结算

AI 不需要“完全自由发挥”，而是要在约束下进行角色化表达：

- 知道什么
- 不知道什么
- 可以说什么
- 不能主动说什么
- 在什么压力下会松口

只要这些边界控制住，AI 角色就会更稳定，也更像真实玩家。

## 3. 产品形态升级

建议产品链路调整为：

1. 首页进入
2. 选择副本
3. 查看副本简介
4. 选择或抽取角色卡
5. 阅读公开设定与私密任务
6. 进入正式对话场
7. 伴随阶段推进、线索投放、气氛变化完成推理
8. 指认 / 复盘 / 结局结算

## 4. 核心玩法原则

### 4.1 用户不是旁观者，而是局中人

用户可能扮演：

- 普通角色
- 真凶
- 帮凶
- 知情者
- 误导型角色

### 4.2 用户视角必须隔离

用户拿到的是“角色卡视角”，不是完整剧本底稿。

即使用户抽到凶手，也只能看到：

- 自己做了什么
- 自己为什么这么做
- 自己担心什么暴露
- 自己可采用的伪装策略

而不是全局所有人的秘密。

### 4.3 AI 角色不应完全自治

第一阶段不建议直接做“多个平等 Agent 自主开会”。

更合理的是：

- `Director / GameMaster`：掌握真相、阶段、规则与边界
- `CharacterResponder`：以指定角色视角生成发言
- `RuleGuard`：处理越权、剧透、跳关、元指令攻击
- `SessionState`：保存每局状态

也就是“单总控 + 多角色视角生成”，而不是“完全自治多 Agent 社会模拟”。

## 5. 领域模型建议

### 5.1 ScriptDefinition

副本静态定义：

- 副本 ID
- 副本名
- 副本简介
- 开场氛围
- 主持角色
- 真相底稿
- 阶段列表
- 角色列表
- 线索列表

### 5.2 CharacterDefinition

角色静态定义：

- 角色 ID
- 角色名
- 身份
- 与死者 / 核心事件关系
- 对外人设
- 已知事实
- 隐藏秘密
- 禁止主动透露的信息
- 公开目标
- 私密目标
- 公开背景
- 私密背景
- 是否可被玩家扮演
- 是否为凶手
- 是否为帮凶

### 5.3 StageDefinition

阶段控制定义：

- 阶段 ID
- 阶段名
- 阶段顺序
- 阶段目标
- 阶段开场旁白
- 本阶段可公开线索
- 本阶段重点角色
- 推进关键词
- 最少轮次要求
- 下一阶段条件说明

### 5.4 GameSession

单局运行时状态：

- 会话 ID
- 当前副本 ID
- 玩家所扮演角色 ID
- 玩家角色名
- 玩家当前目标
- 当前阶段
- 已公开线索
- 角色状态
- 对话历史
- 环境摘要
- 剧情节拍
- 待投放场景提示

## 6. 规则守卫必须存在

用户可能出现：

- 直接索要真相
- 越权发言
- 强行跳剧情
- 元指令攻击
- 自爆或故意脱离世界观

所以必须对输入做分类：

- 正常发言
- 提问角色
- 搜证请求
- 指控 / 投票
- 剧透请求
- 跳关请求
- 破坏沉浸的元指令

系统要根据分类决定：

- 正常推进
- 柔性拦截
- 管家控场
- 触发结局
- 收束回规则边界

## 7. 可选副本平台化方向

系统不应绑定单一剧本，而应支持副本目录。

第一阶段建议支持：

- 列出副本
- 查看副本可扮演角色
- 选择副本
- 初始化角色卡
- 进入会话

后续再扩展：

- 随机抽卡
- 难度标签
- 副本分类
- 结局统计

## 8. 新副本方向：《雪夜借宿》

### 8.1 背景

几名各怀目的的登山者在暴雪封山之夜借住山中旅舍。凌晨后，命案发生。通信中断、道路封死，所有人被困在雪线之上。

### 8.2 气质

- 封闭空间
- 风雪压迫
- 借宿关系脆弱
- 每个人都不像表面那样简单

### 8.3 适合作为首批模式 A 副本的原因

- 易于制造封闭场景
- 角色聚集合理
- 每个人都能有真实秘密
- 适合做环境变化与阶段压迫
- 非常适合 AI 多角色试探和对质

## 9. 《雪夜借宿》第一版角色建议

建议总人数 6：

- 用户可扮演角色 5 人
- 主持 / 接待角色 1 人

可扮演角色示例：

- 摄影记者
- 户外领队
- 药企销售
- 地质研究生
- 民宿老板娘

主持角色示例：

- 山舍老板 / 管事人

## 10. 后端首轮落地目标

本轮后端应该先完成这些骨架能力：

1. 支持多副本仓储
2. 支持列出副本目录
3. 支持查看副本可扮演角色卡
4. 支持初始化会话时绑定副本与角色
5. 会话状态记录玩家当前扮演身份
6. 对话编排改为读取玩家角色卡，而不是写死“中立调查者”
7. AI 讨论名单中排除玩家本人，避免 AI 替用户说话

## 11. 暂不建议过早做的事情

- 完全自治多 Agent
- 所有角色自由抢话
- 长链路复杂搜证系统
- 数据库存档与向量检索先行
- 过度前端特效先于玩法闭环

当前阶段更重要的是把：

- 角色视角
- 信息隔离
- 阶段推进
- 守卫兜底
- 结局判断

这几件事做扎实。

完成本轮骨架后，建议继续推进：

1. 把《雪夜借宿》补齐完整角色表
2. 设计每个角色的完整角色卡
3. 设计第一版胜负条件
4. 增加“抽卡模式”
5. 增加“搜证 / 指控 / 申请公开线索”动作层
